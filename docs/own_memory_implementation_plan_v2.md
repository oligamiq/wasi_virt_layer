# Own-Memory Mode Implementation Plan V2

ユーザーのご指摘の通りです。前回の計画には `wasi-libc` の挙動に対する重大な見落としがありました。

## 前回の計画の欠陥
前回の計画では「ターゲット内部の `memory.grow` を完全に無効化（`-1` を返す）する」としていました。
しかし、`wasi-libc` のアロケータ（`dlmalloc`）は、利用可能な空きメモリ領域を認識するために `memory.size` を使用するのではなく、**初期化時に `memory.size` をヒープの終端（`brk`）として記憶し、それ以降の割り当て（`malloc` やスレッドスタック用の `mmap` 等）には必ず `memory.grow` を呼び出す**という仕様になっています。

そのため、VFS側でいくら物理メモリを拡張（シフト）しても、ターゲットWasmの `memory.grow` が `-1` を返す限り、ターゲットはメモリを確保できず必ず失敗（`EAGAIN`）してしまいます。

## 立て直した新しい計画（論理サイズと物理サイズの完全分離）

`--own-memory` の本来の目的「ターゲットによる物理的な自動拡張を防ぎつつ、VFSが安全にメモリ枠を管理する」を達成するためには、ターゲットに対して「物理的な `memory.grow`」ではなく「**論理的なクォータ（割り当て枠）内での疑似的な `memory.grow`**」を提供する必要があります。

### 1. 新規グローバル変数の追加
各Wasmモジュールに対し、オフセットを管理する既存のグローバル変数（`this_gid`）に加えて、**「現在の論理メモリサイズ（ページ数）」を追跡する新しいグローバル変数（`logical_size_gid`）を追加**します。初期値はパース時のメモリサイズ（例: 17ページ）です。

### 2. ターゲット内部の `memory.size` の置換
追加した `logical_size_gid` の値をそのまま返すように置換します。
これにより、`wasi-libc` は起動時に自分自身の正しい初期ヒープサイズを認識します（VFSが事前確保した全体サイズと混同しません）。

### 3. ターゲット内部の `memory.grow` の置換
物理的な `memory.grow` は呼び出さず、以下の論理チェックを行う処理に置換します。

1. **利用可能な最大サイズの計算**:
   - 最後のモジュール以外: `(next_gid - this_gid) / 65536`
   - 最後のモジュール: `物理的な memory.size - (this_gid / 65536)`
2. **拡張可否のチェック**:
   `現在の論理サイズ (logical_size_gid) + 要求ページ数 <= 利用可能な最大サイズ`
3. **成功時**:
   `logical_size_gid` を更新し、更新前の `logical_size_gid` を返す。
4. **失敗時 (クォータ超過)**:
   `-1` を返す。

### 4. VFSから呼ばれるエクスポート版 `memory_grow`
これは物理的な `memory.grow` を実行し、後続のモジュールのオフセット（`next_gid` 等）をシフトします。
これにより、ターゲットモジュールの「利用可能な最大サイズ」が物理的に広がりますが、ターゲットの「現在の論理サイズ (`logical_size_gid`)」は変化しないため、ターゲットは後から自身の `memory.grow` を通じて安全にその領域を消費（割り当て）できるようになります。

---

この再設計により、ターゲットWasmの `wasi-libc` は「自分自身で `memory.grow` を実行してメモリを確保している」と認識し正常に動作しますが、実際にはVFSが事前に確保した物理メモリの枠内（クォータ）を消費しているだけになります。これにより、ご指摘の問題が完全に解決されます。
